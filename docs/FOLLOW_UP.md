## 待办详情与验收要求

### F01：稳定 ID、手动分组和重新导入

位置：`src/LibraryManager.cpp::mergeTrack`、`src/Track.cpp::normalizedKey`。

- 当前合并优先匹配音频路径，再匹配 `artist + album + title + disc + track + year`，没有完整的稳定 ID 对应策略。
- 手动整理改变专辑名称/年份后，同一曲目若来自另一个解包目录，原 ID 可能仍相同，但路径和元数据键都不同；当前会作为新曲目加入，并在 ID 冲突时生成新 ID。
- 已保存的两个独立曲目如果元数据键恰好相同，之后从不同路径合入另一个版本，也需要避免错误归属音质。
- 下一步：设计 ID 匹配、冲突检测和源记录映射。不能直接把所有“ID 相同”都认定为同一录音。
- 验收：手动改名/合并后导入另一个路径的同源包，不重复添加；外部 ID 冲突不吞曲目；合并后歌单 ID 和音质归属正确。

### F02：旧脚本与应用行为不一致

位置：`scripts/merge_import_library.js`、`scripts/normalize_album.js`。

- 命令行合并脚本仍逐项 `findIndex`，大型曲库存在二次复杂度；相对路径按进程工作目录解析；命中时直接替换整条记录；写文件也不是原子替换。
- 归一化脚本仍按 `artist + album + title` 合并，未区分碟号、曲序、年份和手动分组，可能合并两首同名录音或使歌单引用的 ID 消失。
- 下一步：与 C++ 规则统一，增加输入校验、路径基准、ID 保留、索引和原子写入；必要时将旧脚本标为不适合直接修改正式曲库。
- 验收：同名多碟、不同年份、手动整理、相对路径、保存失败的用例全部保留曲目及原有有效引用。

### F03：多实例写入冲突

位置：`src/main.cpp`、`src/LibraryManager.cpp`、`src/PlaybackQueue.cpp`。

- `QSaveFile` 防止单次写入留下半个文件，但不防止两个应用实例分别保存自己的旧快照。
- 下一步：确定单实例入口，或用文件锁加版本/修改时间冲突检测；曲库和歌单需要一起考虑。
- 验收：第二个实例不会无提示覆盖第一个实例刚保存的整理结果。

### F04：同步 API 的事务边界

位置：`scanFolder`、`importLibrary`、`mergeLibrary`。

- 当前 QML 使用 `startOperation`：在后台副本操作，保存成功后才发布到前台，保存失败回滚用例已通过。
- 这些同步公共方法直接被调用时，仍先修改自己的模型再保存，失败后内存可能已改变。
- 下一步：收紧同步 API 的可见性，或抽出无 UI 的结果对象，所有调用统一执行“准备结果 → 持久化 → 发布”。
- 验收：直接调用同步 API 时，模拟无法写入目标文件，内存及磁盘均保持原值，不发出误导性的成功更新。

### F05：旧曲库的专辑归属

位置：`AlbumModel.cpp::groupingKey`、`LibraryManager.cpp::refreshAlbumMetadata`。

- 本轮读取的旧曲库有 1,655 首，旧数据没有 `albumArtist`；按歌手和专辑名共有 1,261 组，139 个专辑名涉及多位歌手。这只能说明存在合辑候选，不能直接断定应全部合并。
- 已增加“更多操作 → 补全专辑标签”，只补缺失的专辑艺术家，保留手动归组；实际标签中没有该字段时仍需用户确认。
- “归并同目录合辑”只处理同目录、同名、同年份且没有专辑艺术家的曲目。跨目录的合辑不会自动合并。
- 同一专辑部分曲目年份缺失、其他曲目年份已知，当前仍可能分成两组；不同发行版本则应保持独立。
- 下一步：增加带预览的合辑候选和年份缺失归并策略，显示每首歌的归属依据；研究多碟目录的共同父目录，而不是无条件按同名合并。
- 验收：缺年份、合辑、多碟、重制版、无标签曲目均有样本；预览准确，确认前不修改曲库。

### F06：跨 ZIP 的重复资源

位置：`zipCacheDirFor`、`mergeLibrary`、`mergeTrack`。

- 选择性解包已保留，但不同 ZIP 的缓存根不同。相同音频在另一个包中会得到不同路径，仍可能被复制并作为另一音质加入。
- 曲目数量不增加，不代表资源没有重复，不能把当前实现描述成“按内容去重”。
- 下一步：设计资源内容索引和校验缓存；先按大小等廉价条件筛选，再校验内容。不可仅凭文件名、码率或 CRC 就删除/复用不同录音。
- 验收：两个不同包重复包含相同音频时，确认文件实际读取量、写入量、缓存占用和音质数量；同名但内容不同的音频仍保留。

### F07：ZIP 缓存维护与校验范围

位置：`readStoredZipEntry`、`extractSelectedZipEntries`、`mergeLibrary`。

- 新读取的索引和新解包资源已校验 CRC，并检查包内路径；不过选择性合并会跳过已经存在的缓存文件，未再次验证这些文件是否完整或被修改。
- 失败或不再引用的包可能留下缓存；尚无引用分析和回收入口。
- 下一步：定义可信缓存标记/校验记录；补截断缓存、内容被改、符号链接、畸形目录和解包失败的测试；回收时只处理确认无引用的缓存。
- 验收：损坏缓存能够修复或明确报错；失败操作不会影响现有曲库；回收不删除播放中或仍被引用的文件。

### F08：任务进度、取消和关闭窗口

位置：`LibraryManager::startOperation`、`qml/Main.qml::onClosing`。

- 现在长任务不会直接占用 UI 线程，但只显示阶段文案和不确定进度条；运行期间不允许关闭窗口，没有取消入口。
- 下一步：以文件/字节为单位报告进度，在安全边界支持取消；区分“完成当前文件后退出”和立即放弃未提交结果。
- 验收：大目录扫描及大 ZIP 合并时仍能播放、暂停、搜索；取消不发布半成品，关闭行为清晰。

### F09：剩余性能路径

位置：`commitTracks`、`ScriptBridge::runScript`、`readAlbumSidecar`、`Track::primaryPath`、`addZipFile`。

- 专辑编辑/合并/移除和 JS 整理仍可在 UI 线程做全量序列化或脚本执行；文件越大，成本越明显。
- 索引仍为整库 JSON，每次修改重写全库；扫描会重复读取同目录的专辑 sidecar；播放路径选择仍有文件存在性检查。
- ZIP 导出先读文件计算 CRC，再读一次写入，可研究单次读取后回填 ZIP 头；当前尚未实现。
- 下一步：先采样分析主线程耗时、磁盘读取量和峰值内存，再决定后台化、缓存或增量存储；不要未经测量就直接改数据库。
- 验收：记录 1 千/1 万/3 万首，以及真实大 ZIP 的耗时、UI 最大停顿、峰值内存和读写量。

### F10：撤销与历史合并拆分

位置：`m_undoTracks`、`undoLastEdit`、`startOperation` 完成回调。

- 当前撤销仅有进程内的一步快照，成功的后台任务会清除它；重启后不能撤销。
- 移除曲库记录时队列会清除失效项，撤销曲库移除不会恢复之前的队列状态。
- 历史合并没有逐曲目拆分入口，恢复单个来源专辑不够方便。
- 下一步：增加明确的撤销范围提示、合并历史或可编辑的曲目归属；优先保证历史操作不覆盖后来导入的数据。
- 验收：合并、编辑、删除、导入交错执行时，撤销与拆分的影响范围可预期。

### F11：UI 与播放体验继续验证

位置：`qml/Main.qml`、`PlayerController.cpp`、`PlaybackQueue.cpp`。

- 已修复小窗口歌单面板无法容纳所有控件和空 ID 造成的误高亮。
- 真实封面在异步加载初期会显示占位，测试中等待约 2.5 秒后首屏封面完成；还没有持久缩略图缓存。
- 小窗口歌词面板以覆盖方式展示，仍需验证鼠标、键盘焦点和返回操作；长专辑名、合并目标输入、空状态的文案和布局也应继续检查。
- 最后一轮修正了软件渲染下弹窗背景和一个枚举赋值问题，加载冒烟测试通过；最终弹窗样式仍建议重新截图确认。
- 自动续播、损坏音频连续跳过、播放途中删除曲目/切换歌单、音频设备切换、睡眠恢复尚未完整覆盖。
- 下一步：用真实操作复现具体问题，补行为测试；无需为此继续无目的更换视觉风格。

### F12：同步文档

位置：`README.md`、`docs/LIBRARY_SCHEMA.md`。

- 部分说明仍写“顶部按钮”和旧的三字段曲目合并规则。
- schema 文档尚未完整解释 `albumArtist`、`albumId`、元数据分组与手动分组的优先级、年份/碟号/曲序、保留 ID 和撤销边界。
- 下一步：按最终实现更新用户操作入口和 schema 示例，并说明旧曲库迁移办法。
- 验收：新用户能仅凭文档完成添加音乐、补全标签、预览合并、撤销和导出。

### F13：验证与兼容性边界

- ZIP 仍只支持本应用导出的 store 格式，不支持普通 deflate、ZIP64、加密条目和数据描述符；索引读取上限为 64 MiB。
- 当前存储格式上限、失败后的资源行为应在导入/导出前给出可理解的提示。
- 尚未完成严格的旧版/新版同输入性能对照，不应宣称已测得具体提速倍数。
- Linux Release 和离屏软件渲染已验证；Windows/macOS、不同 DPI/主题、长时间播放、多实例、巨型真实曲库和发布包仍需测试。
